## 0. 단계 정리

1~4단계 기술 핵심은 완료로 둡니다. 3단계는 실제 MILAL V1 관계망 시각화까지 되었고 HSA3는 읽기 전용 시제품으로 따로 관리합니다. 검색식 개편은 종료 — 이번에 검색식 기능을 더하지 않았고, 계산을 워커로 옮기는 일만 했습니다(결함 발견 시에만 수정).

## 1. 작업 A — Web Worker 적용 (적용함)

**분석.** `app/study_q.js`의 계산부는 전역 `SD`(BHSA 자료)와 `PLAN`(책 이름)에만 의존하는 순수 함수였습니다: `qIndex`(단위별 낱말 CSR 색인) · `qParse` · `qRun`(재귀 탐색, 상한 20,000·단계 4,000,000) · `qHits` · `qWhyIndex` · `qFingerprint` · `qCanon`. DOM·`view`를 건드리지 않으므로 그대로 떼어낼 수 있었습니다.

**구조 (엔진은 하나).**
- `app/study_qe.js` — 위 함수들을 **글자 하나 바꾸지 않고** 옮긴 엔진 파일. 주 스레드(`<script>`)와 워커(`importScripts`) 양쪽이 같은 파일을 읽습니다. 경쟁 엔진은 없습니다. 워커에 없는 `spanVerses`·`slotOf`만 같은 계산의 대체(`qeSpanVerses`·`qeSlotOf`)를 두고, 주 스레드에서는 기존 함수가 있으면 그것을 씁니다.
- `app/study_qw.js` — 워커(약 15줄): 자료 받기 → `qParse`·`qRun`·`qHits`·`qWhyIndex`·`qFingerprint` 실행 → 결과 전송. 묶음(`[단위, 번호]` 배열)은 그대로, Map/Set 은 배열로 바꿔 보냅니다.
- `study_q.js` — `qExec()`: 워커가 되면 워커로, 아니면 `qExecSync()`(같은 엔진, 주 스레드).

**BHSA 자료 전달.** 엔진이 쓰는 것만 보냅니다: 형식 배열 10개(`vOf wl wm wf wc wp ws ct cd pt`, 합 9 MB)와 사전·형태·절 표(`L M V` 등 1.2 MB). 구조 복제(structured clone)로 **24~31 ms**. 책을 더 받아 `SD.loaded`가 바뀌면 key 가 달라져 다시 보냅니다(워커는 자기 쪽 색인 `qi`를 다시 만듦). SharedArrayBuffer 는 GitHub Pages 에서 교차 출처 격리를 켤 수 없어 쓰지 않았습니다.

**응답성·취소·늦은 결과·대체·오류.**
- 실행마다 번호(`S.qSeq`)를 붙이고, 돌아온 결과의 번호가 현재 번호와 다르면 버립니다 → 조건·범위를 바꿔 다시 찾은 뒤 늦게 온 옛 결과가 덮어쓰지 않습니다.
- '찾는 중입니다… 화면은 그대로 쓸 수 있습니다 [취소]' — 취소는 워커를 끝내고(다음 실행 때 새로 만들며 자료 재전송) 이전 결과로 돌아갑니다.
- `Worker` 가 없거나, 워커 생성·전송·실행에서 오류가 나거나, 워커 자료가 최신이 아니면 **주 스레드 엔진으로 바로 대체**(같은 결과). 워커 쪽 계산 오류는 "검색 중 문제가 생겼습니다(워커): …"로 표시. 상한/중단 사유는 기존 문구 그대로("n건 이상 (처음 20,000건까지만)", "n건까지 찾고 중단").
- 시험용 스위치 `localStorage milal-q-worker=off` 로 주 스레드 실행을 강제할 수 있습니다(대조 시험용).

아홉 식 모두 **건수·지문·절·절별 근거가 동일**(지문 예: 예시1 `227:9eccd86bb9ca8f05` 양쪽 같음). 대조 건수 227/369/2260/1015/3697 유지. 보관함 검색식 재실행(워커)도 구약 전체 복원·369건·지문 동일.

**응답성(모바일 에뮬레이션, 계산 중단 사례 ~400 ms):** 주 스레드 실행은 그 동안 화면이 멈춤(최대 프레임 간격 **361 ms**, 프레임 3개) · 워커 실행은 최대 프레임 간격 **24 ms**(프레임 22개), 검색 중 스크롤과 '본문' 탭 이동이 **12 ms** 안에 처리되고 '찾는 중' 표시가 보임. 취소: 누르면 즉시 이전 결과(227건)로 돌아오고 4초 뒤에도 긴 결과가 덮어쓰지 않음. 늦은 결과 방지: 긴 검색 중 조건을 바꿔 짧은 검색을 돌리면 짧은 결과가 남고 옛 결과는 버려짐. 대체 동작: `Worker` 제거·오류 표시 뒤 주 스레드 엔진으로 같은 227건.

**메모리.** 주 스레드 힙은 두 방식 모두 검색 뒤 25~26 MB 로 같습니다(형식 배열은 힙 밖). 워커 쪽에 자료 복사본(9 + 1.2 MB)과 워커 자신의 색인(약 14.7 MB)이 **한 벌 더** 생깁니다 → 약 25 MB 추가. 대신 주 스레드는 워커 모드에서 색인을 만들지 않습니다('맞은 자리'를 열 때 필요하면 그때 만듦). 오래된 저사양 기기에서 이 추가분이 부담이면 스위치로 끌 수 있으나, 기본은 켬.

**평가.** 계산 시간은 워커가 5~40 ms 늦지만(메시지 왕복·복제) 결과는 동일하고, 화면 멈춤이 361 → 24 ms 로 줄어 **적용할 가치가 있다**고 판단해 적용했습니다. 전체 회귀(검색식 34+28, 연구 탭 9, 안정성 23, 모바일 12, 사용성 걸음, 비교기 28+13, 인쇄 6, 대조 건수)가 워커 켠 상태로 모두 통과했습니다.
