# 오프라인(Service Worker) 설계 — 구현 전 설계서 (2026-10-21, 지시 9 작업 D)

상태: **설계만. 운영 배포 없음.** 구현은 실기기 점검(`docs/ANDROID_DEVICE_CHECK.md` 1·2번: 최초·재방문 로딩 측정)이 끝난 뒤 별도 지시로 한다. 이 문서는 "무엇을 어떤 규칙으로 저장하고 언제 버리는가"만 정한다.

## 1. 무엇이 있는가 (현재 앱이 받는 자료)

| 묶음 | 경로 | 크기(대략) | 바뀌는 때 | 지금의 캐시 깨기 |
|---|---|---|---|---|
| 앱 껍데기 | `index.html`, `app/*.js`, `study.css`, 글꼴 | 수백 KB | 코드 수정마다 | `?v=` 번호(파일마다) |
| BHSA 색인 | `study/meta.json`, `study/index.json` | 0.6 MB | BHSA 재생성 때만 | `?v=STUDY_V` |
| BHSA 책별 자료 | `study/books/<b>.json` (39개) | 책당 0.1~1.5 MB, 전체 16 MB | BHSA 재생성 때만 | `?v=STUDY_V` |
| 번역 본문 | `study/bible/krh/<b>.json` | 책당 수십 KB | 거의 없음 | `?v=STUDY_V` |
| 사전 풀이 | `study/lexko.json` | 0.1 MB | 드묾 | `?v=STUDY_V` |
| **MILAL 결과** | `study/milal/job.json` (+ `bhsa_native_job.json`) | 수 MB | 연구자가 새 판을 낼 때 | `?v=STUDY_V` |
| **연구자 승인 기록** | `study/milal/approvals.json` | 작음 | 연구자가 승인할 때 (records 0) | `?v=STUDY_V` |
| 사용자 연구 기록 | IndexedDB `milal-annots`(store `annots`), localStorage `milal-*`(검색식 보관함 `milal-study-queries`, 설정) | 사용자별 | 사용자가 쓸 때 | — (캐시가 아님) |
| 동기화 | Firestore(로그인 때만, `ANNOT_SYNC_ENABLED` 스위치) | — | — | SW 가 관여하지 않음 |

지금도 `?v=` 로 브라우저 캐시를 깨고 있으므로 Service Worker 는 **"끊겨도 열리게"**만 더한다. 자료 판 규칙은 그대로 둔다.

## 2. 캐시 네 통 — 갱신 정책을 서로 다르게

하나의 캐시에 다 넣으면 "앱은 새 판인데 자료는 옛 판"이 생긴다. 통을 나누고 통마다 규칙을 둔다.

| 통 이름 | 담는 것 | 전략 | 버리는 때 |
|---|---|---|---|
| `shell-<APP_V>` | 껍데기(index.html, app/*.js, css, 글꼴) | **설치 때 미리 받기(precache)**, 요청은 캐시 먼저 | 새 SW 가 활성화되면 옛 `shell-*` 삭제 |
| `bhsa-<STUDY_V>` | meta/index/books/bible/lexko | **캐시 먼저, 없으면 네트워크 뒤 저장**(책은 사용자가 연 것만 — 전체 16 MB 를 미리 받지 않음; '구약 전체 받기'는 사용자가 눌렀을 때만) | STUDY_V 가 바뀌면 옛 통 통째로 삭제 |
| `milal-<STUDY_V>` | `job.json` + `approvals.json` + `bhsa_native_job.json` **세 파일을 한 묶음으로** | **네트워크 먼저, 실패하면 캐시**(stale-while-revalidate 금지 — 아래 3절) | STUDY_V 가 바뀌면 삭제 · 묶음이 깨지면(한 파일만 새로 받아짐) 묶음 전체를 다시 받을 때까지 옛 묶음 유지 |
| (없음) | IndexedDB·localStorage | SW 가 **절대 만지지 않음** | — |

`APP_V`(코드 판)와 `STUDY_V`(자료 판)는 지금처럼 `index.html` 에 적고, SW 파일은 두 값을 읽어 통 이름을 만든다.

## 3. MILAL 결과와 승인 기록이 다른 판으로 섞이지 않게

위험: `job.json` 은 캐시(옛 판), `approvals.json` 은 네트워크(새 판) — 또는 그 반대. 지금 앱은 승인 기록을 **파일 sha256 으로 대조**하므로(`app/milal.js`: 파일 안 `review.status` 를 믿지 않고 `approvals.json` 의 `file_sha256` 이 같은 기록만 인정) 섞여도 "잘못 승인됨"은 나오지 않고 "승인 없음"으로 떨어진다. 그래도 사용자가 "승인이 사라졌다"고 오해할 수 있으므로 설계로 막는다.

규칙:
1. 세 파일은 **같은 STUDY_V 통**에만 산다. 앱은 세 파일을 `?v=STUDY_V` 로 함께 요청한다.
2. SW 는 이 통에 대해 **네트워크 먼저**: 셋 다 받아지면 셋을 한꺼번에 통에 넣는다(한 파일이라도 실패하면 **통을 갱신하지 않고** 옛 묶음 셋을 그대로 돌려준다 → 항상 같은 묶음끼리).
3. 앱 쪽 표시: `job.json` 의 sha256 과 `approvals.json` 의 `file_sha256` 이 다르면 지금처럼 "이 파일에 대한 승인 기록 없음"으로 보이고, 오프라인이면 거기에 "(오프라인 — 저장된 판 기준)"을 덧붙인다.
4. 승인 기록은 **네트워크에서 온 것만** 승인으로 보인다는 원칙은 두지 않는다(오프라인에서도 같은 묶음이면 유효). 대신 화면에 자료 판(STUDY_V)과 파일 sha 앞 8자를 적어 연구자가 어느 판을 보는지 알 수 있게 한다(이미 구조 탭 머리에 판이 표시됨).
5. 캐시를 쓴 응답에는 응답 머리 `X-MILALWV-Cache: <통 이름>` 을 붙여, 앱이 "저장본을 보는 중"을 알 수 있게 한다.

## 4. 사용자 기록 보호

- SW 의 `activate` 는 `caches.keys()` 가운데 **`shell-`, `bhsa-`, `milal-` 접두어**만 지운다. `indexedDB.deleteDatabase`·`localStorage.clear` 는 SW 코드에 없다(코드 검토 항목).
- 브라우저의 "저장소 비우기"는 캐시와 IndexedDB 를 함께 지울 수 있으므로, 사용자 안내에 "오프라인 자료만 지우려면 메뉴의 '저장된 원문 자료 지우기'를 쓰세요"를 둔다(앱 메뉴에 캐시만 지우는 단추 추가 — IndexedDB 는 건드리지 않음).
- `navigator.storage.persist()` 를 로그인·첫 메모 저장 때 한 번 요청한다(브라우저가 저장소를 임의로 비우는 것을 줄임). 거절되어도 동작은 같다.
- 기록 탭의 JSON 백업·복원은 지금처럼 유지(오프라인에서도 됨 — 파일 API 는 네트워크 불필요).

## 5. 끊겼을 때 화면

- 받은 적 없는 책을 열면: "이 책 자료가 아직 기기에 없습니다. 인터넷에 연결하면 받습니다"(지금 로딩 오류 문구를 그대로 씀, 재시도 단추).
- 검색식 '구약 전체': 받은 책이 39권 미만이면 지금처럼 "n/39권 받는 중" — 오프라인이면 "받은 책(n권) 안에서만 찾기" 단추를 두되, 결과 범위 이름을 **"받은 책 n권"**으로 적어 '구약 전체'로 보관·메모되지 않게 한다(검색 범위 명칭 원칙, 지시 8).
- 머리띠에 작은 "오프라인" 표시. 동기화(Firestore)는 로그인 상태에서도 멈추고, 연결되면 지금의 큐가 그대로 보낸다(SW 와 무관).

## 6. 판 올리기 절차

1. 자료를 바꾸면 `STUDY_V` 올림(지금 규칙) → 새 `bhsa-`·`milal-` 통이 생기고 옛 통은 activate 때 삭제.
2. 코드를 바꾸면 `APP_V` 올림 → 새 SW 설치, 사용자에게 "새 판이 있습니다 — 새로 고침" 띠(강제 새로 고침 없음, 작성 중인 메모를 잃지 않게).
3. MILAL 결과만 새 판일 때도 `STUDY_V` 를 올린다(세 파일 묶음 규칙 때문에 부분 갱신은 두지 않는다).

## 7. 구현 전에 재야 할 것 (실기기)

- 최초 로딩·재방문 로딩 초(점검표 1·2) — SW 없이 얼마나 느린지 모르면 SW 의 효용을 말할 수 없다.
- 기기 저장 공간: 전체 책 16 MB + MILAL 수 MB 가 Android Chrome 의 저장 한도에서 문제없는지(`navigator.storage.estimate()` 값을 점검표에 추가).

## 8. 하지 않는 것

- 전체 자료를 처음부터 미리 받기(모바일 데이터 낭비).
- MILAL 결과·승인 기록의 부분 갱신, `stale-while-revalidate`.
- IndexedDB·localStorage 를 SW 가 읽거나 지우기.
- Firestore 요청을 SW 가 가로채기.
